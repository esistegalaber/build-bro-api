This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Build Bro is a Spring Boot 4.1 (Java 17+) REST API that tracks CI builds, build numbers, build-set templates ("environments"), servers and deployments. It is backed by MariaDB with Flyway migrations. Tests are written in Groovy with Spock.

## Commands

```bash
./mvnw verify                        # compile + run all tests + JaCoCo report (target/site/jacoco)
./mvnw test                          # tests only
./mvnw test -Dtest='BuildEndpointImplSpec'          # single spec
./mvnw test -Dtest='BuildEndpointImplSpec#Search'   # single feature method
./mvnw spring-boot:run               # run the API on :8080
./mvnw verify sonar:sonar            # what CI runs on GitHub Actions
```

Maven needs **JDK 17 or newer** (`JAVA_HOME`). CI builds with JDK 21. Spock specs (Groovy 5, `spock-*-groovy-5.0`) in `src/test/groovy` are compiled by `gmavenplus-plugin`, and Surefire is configured to pick up both `*Spec` and `*Test` classes.

**Tests and the app need a running MariaDB.** There is no in-memory DB or Testcontainers. `application.properties` expects `jdbc:mariadb://localhost:3306/build_bruh` with user/password/database all set to `build_bruh`. Start one with:

```bash
docker run --name build_bruh_db -d -p 3306:3306 -e MYSQL_DATABASE=build_bruh -e MYSQL_USER=build_bruh \
  -e MYSQL_PASSWORD=build_bruh -e MYSQL_ROOT_PASSWORD=build_bruh mariadb:10.10
```

(`setup-db.sh` does roughly the same but uses an inconsistent container name and a `build_bruh` docker network. Create that network first or use the command above.)

Docker image: `./mvnw package`, then build the `Dockerfile`, which copies `target/build-bro-api-0.2.0.jar`, so update the Dockerfile when `<version>` changes in `pom.xml`. At runtime it takes `DB_URL`, `DB_USR` and `DB_PWD` env vars.

## Architecture

Package root: `com.egalaber.buildbro`. Requests move through these layers:

1. **`api.v1`**: endpoint *interfaces* hold all Spring MVC mappings (`@GetMapping("/api/v1/...")` etc.). **`api.v1.impl`**: `@RestController` classes implement them and contain no mapping annotations. Add new routes to the interface.
2. **`api.model`**: API DTOs, all prefixed `I` (`IBuild`, `IBuildSearch`, …). The prefix does not mean they are interfaces; they are Lombok classes. `BaseSearch` provides paging (`page()`) for search requests.
3. **`core.service`**: business logic. Services take and return API models (or `Page<Entity>` for searches) and convert using static mappers in **`core.mapping`** (`XMapper.toApi(...)`).
4. **`core.repository`**: Spring Data JPA repositories plus `*Specs` classes of static `Specification` factories. Queries are built by composing specs (see `BuildService.toSpecification`), not with derived query methods or JPQL. Specs use the Hibernate JPA metamodel (`Build_`, generated by `hibernate-processor` at compile time, configured as an annotation processor in `pom.xml`), so a clean compile is needed after entity changes.
5. **`core.domain`**: JPA entities. The schema is owned by Flyway (`src/main/resources/db/migration`) and Hibernate runs with `ddl-auto=validate`. **Every entity change needs a new `V*__*.sql` migration.**

Cross-cutting pieces:
- **Errors**: throw subclasses of `api.fault.BuildBroException` (`DataNotFoundException`, `InvalidRequestException`). These are checked exceptions that carry an HTTP status. `BuildBroExceptionHandler` turns them into `IExceptionInfo` JSON responses.
- **Events**: `BuildEndpointImpl.create` publishes `BuildCreatedEvent`. `BuildCreatedEventListener` (`@Async`, enabled via `@EnableAsync`) calls `TrackingService`, which auto-creates the `Project`/`Branch` rows for the build. Projects and branches therefore come into existence as a side effect of build creation.
- **Logging**: `core.aop.LoggingAspect` (registered via `@Import` in `BuildBroApiApplication`) logs every method result and exception in `core.service.*` and `api.v1.impl.*`.
- OpenAPI/Swagger UI comes from springdoc.

## Tests

- `BaseBuildBroSpec`: `@SpringBootTest` + `@Transactional` service-level specs.
- `BaseRestSpec`: boots the server on the real port (`DEFINED_PORT`, 8080, so it will clash with a locally running app) and calls `/api/v1` through `TestRestTemplate`. In Boot 4 that class lives in `org.springframework.boot.resttestclient` and needs the `spring-boot-resttestclient` and `spring-boot-restclient` test dependencies. It is not transactional.
- Both run `@Sql('/testdata.sql')` before each feature. That script deletes all tables and reseeds fixtures, so assertions rely on its data (e.g. project `backend`, branch `main`). When adding tables, add them to the delete list in FK-safe order.
- `EqualsAndHashCode*Test` use EqualsVerifier on all domain entities and API models. New entities and models must satisfy it.
